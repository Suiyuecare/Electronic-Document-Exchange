# 三種使用情境改善與發布驗收

日期：2026-09-22。此文件為發布候選版的問題清單與驗收規格；正式部署證據須另以部署 ID、提交 SHA 與正式網域核對結果判定，不由本文件推定。

## 已確認問題與驗收標準

| 角度 | 優先序／問題 | 驗收標準 |
| --- | --- | --- |
| 使用者 | P1：送簽 A 文件期間切至 B 草稿，A 的延遲回應可能誤鎖 B 並跳回 A | 成功、失敗及清理回應只更新原文件／原登入範圍；新草稿可編輯、不誤送、不被舊回應跳頁 |
| 主管簽核 | P1：完成紀錄以原指派人代替實際代理簽核人 | 待處理顯示指派人；完成顯示不可變證據中的實際操作人；舊資料無證據不能臆造 |
| 資料回溯 | P2：只呈現目前流程，缺少退回／加簽／抽單前歷代關卡 | 歷史預設收合，可依輪次查看指派人、實際操作人、完整日期時間、原因；當前決策區不混入歷史按鈕 |
| 資料回溯 | P1：指定用印檔缺失時可能退取舊版當最終檔 | 只接受後端核定的精確檔案 ID；未核定或檔案缺失時不產生替代版下載，明確提示重新載入／聯絡管理員 |
| 主管／資料回溯 | P1：流程或操作紀錄超過 200 筆時截斷，可能漏掉最新代次 | 依案件穩定分頁讀取，超過 200 筆仍取得最新關卡及實際簽核證據；超出安全界限時明確拒絕，不以不完整資料判定權限 |
| 主管簽核 | P2：同案被其他人先處理後，衝突訊息留下過期操作畫面 | 409 後只在相同登入／案件範圍重新讀取最新狀態，要求重新檢閱，不自動重送任何簽核動作 |
| 使用者 | P2：簽核紀錄提示收件，但必須回電子用印的收合清單才能確認 | 在簽核紀錄提供原申請人專用的「確認收件」；沿既有收件權限及 API，完成後重載仍為結案且可下載 |

## 共通驗收

- 合成案件實際完成編輯、送簽、主管逐關檢閱、用印及成品下載。
- 退回上一關、通過並加簽、抽單重送保留歷史與不可變原稿；新流程設定不覆寫已送案件快照。
- 桌機與手機尺寸檢查可讀性、觸控、橫向溢出，保留相同合成資料的改善前／後畫面。
- 保留所有既有回歸及資料庫安全檢查；不得放寬跨公司／租戶限制、自簽限制、檢閱證據或 RLS。
- 正式案件只讀，不以真實公文、員工個資或公司印章製作測試案件。正式電子公文交換維持 Mock／停用。

## 發布順序與判定

1. 原工作目錄不變；隔離分支完成修復、回歸及實際瀏覽器驗收。
2. 比對正式專案、現行部署及資料庫 namespace，確認回復點／備份。
3. 核對來源雜湊與前向 migration；僅更新已核准的 `edoc`／`edoc_private`，不重跑 bootstrap，不改 Finance 主資料。
4. 遠端 CI 與安全檢查通過後發布；核對正式網域對應新部署、提交 SHA、靜態資源版本與健康檢查。
5. 明確區分隔離完整流程測試、正式唯讀驗證及尚未驗證的真實帳號／裝置情境。

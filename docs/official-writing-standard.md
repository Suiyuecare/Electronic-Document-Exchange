# 公文擬稿與輸出版式

## 依據與適用範圍

本次依使用者提供之《公文撰作解析》調整公文擬稿規則及正式函稿版面。參考範圍為教材的公文用語、主旨／說明、日期數字及分項格式；原教材保持唯讀，不隨應用程式部署、不傳送整份教材至外部 API。

適用於新產生的草稿與可編輯的退回案件。不重新製作已送審、已核准或已用印的既有版本，不變更正式電子交換能力。

## 沿用 API

- 保留既有 `/api/ai/compose` 及既有 OpenAI Responses API 呼叫方式。
- 沿用環境中既有的金鑰、模型與逾時設定；不新增憑證、不改資料庫結構。
- 增加發文日期、發文單位及真實附件檔名的擬稿脈絡。
- 日期、文號、金額與辦理狀態須保真。未提供的附件、核准結果或法規依據不得補造。
- AI 文字未通過檢查或服務失敗時，使用本機規則備援，並明示「非 AI 生成」。

## 文字與人工確認

- 主旨重新整理案由與期望，不只把白話原文包上「有關／請查照」。
- 說明一事一點，依實際內容編號，不硬塞三點，不加入空泛依據。
- 發文日期早於所引「已完成」事件日期時，保留原始資料、提出核對提醒，不擅自修正日期或認定已核准。
- 有提醒、或等待生成期間使用者已改動文字／日期／附件時，建議不自動覆蓋原文；使用者可確認套用、保留原文或復原。
- 自動檢查只能協助攔截常見錯誤，不能代替人工作成、核准或法律判斷。

## 版面

- 正式黑白楷體，A4 本文區左右及底部 25 mm。
- 標題 20 pt、受文者與主文 16 pt、聯絡與發文資料 12 pt；長標題換行，不縮小字級。
- 說明／辦法／擬辦／核復事項分節；四層分項使用懸掛縮排。
- 短段落跨頁保護、延續行對齊、聯絡資訊不超出右邊界。
- 極端長度的首頁聯絡資訊或附件說明仍須人工查看 PDF；本輪未重構首頁資訊跨頁機制。

## 驗證方式

- `python -m unittest discover -s tests -p 'test_*.py'`
- `python tools/verify_compose_layout_browser.py --root . --output /tmp/edoc-writing-qa --save-flow --writing-rules`
- `tools/verify_official_pdf_reference.py` 產出去識別化短函、長標題及多頁函稿供逐頁視覺驗收。

測試使用隔離帳號與資料。API 回歸以 mock 驗證既有 endpoint／模型／稽核合約；不藉驗收向外發送正式公文或通知。

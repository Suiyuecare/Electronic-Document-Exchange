| F03 | 已分派收文不易重新分派；離職承辦缺少提示 | 開放未結收文重新分派；後端依現行人員啟用、公司及 tenant 判斷待交接；舊姓名及兩次分派稽核均保留 |
| F04 | 收文匯出只顯示成功提示，未真正提供檔案 | 產生目前篩選範圍的 CSV；欄位引號轉義並防止試算表公式注入 |

| F06 | 部門分析採固定舊單位，無法反映新組織 | 改由已載入的 Finance 人員及收文單位計算；不捏造人數或宣稱全域完整統計 |

| F10 | 手機資訊卡的長名稱超出卡片，回文狀態顯示英文 | 共用資訊卡補上可換行及最小寬度；回文狀態中文化。後續瀏覽器驗收資訊卡內溢出為 0 |

## 五、上線前仍需處理

### A. 政府正式交換：停止啟用

依 `AGENTS.md`，必須取得機關 jAgent／API／SDK／封包規格，完成正式 provider 的測試，再取得人工核准。不得假設 REST、發明正式格式、用 Mock 成功充當正式送達。本次沒有連政府正式交換環境。

### B. 離職未結簽核：須定義接手政策

新案件會依新組織產生流程，但已送簽案件保留當時責任人，不會隨名冊異動自動改寫。收文承辦本次已可重新分派；已鎖定簽核的移交是不同的高風險操作。

現有申請人仍啟用時，可使用既有「抽單 → 確認 Finance 關係 → 重新送簽」，保留舊版簽核歷程。申請人也離職時，不應讓任意管理者冒充本人或覆蓋舊決定；需要確認由誰移交、哪些角色可辦理，以及新一輪哪些關卡必須重簽，再實作具理由、版本比較、完整稽核與交易保護的移交機制。此項目前未完整解決，不能承諾人員任意進出時所有舊單都會自動正常完成。

### C. 正式業務驗收與運維

須完成真實 Finance 登入／跨模組免重登，正式 Storage 上傳／開檔／下載、正式測試用印全流程及收文派發回文；以明確標記的去識別案件進行，避免通知或文件誤寄。補跑本次跳過的本機 RPC／競爭測試、確認備份還原及值班責任。靜態介面稽核項目另列治理清單，不以本次小幅修正宣稱全面符合。

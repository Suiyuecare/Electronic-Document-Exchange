# 人員異動、未結案件交接與真實 SSO 驗收

狀態：製作與隔離驗證中；未發布。正式電子公文交換環境不在本次範圍。

## 已核准規則

- Finance 為人員、公司、組織及啟用狀態的權威來源。
- 總務提出交接，行政部門主任確認；不得同一人提出與確認。
- 接任人須為同公司、同 Finance 租戶的有效人員，且具該關權限。
- 原申請人、已完成簽核的實際行為人、原文件及紀錄不可改寫。
- 離職申請人的退回補正：接任人建立關聯原案的新申請，原案保留，
  新案重新配號、重新完整簽核；不可繼承原案的核准或用印結果。
- 簽核、交接、抽單競爭時，僅一個版本可提交；舊檢視證據不得套用新關卡。
- 已用印或寄送的案件只交接追蹤責任，不改核准、不再次用印或寄送。
- 有權限者跨模組與新分頁可延續已驗證登入；不能以快取繞過停權。

## 實作分段

1. 建立共用、可測試的交接規則／新簽核代次規劃器；先鎖定禁止條件。
2. SQLite 與 Supabase 原子提交、後端 API、授權及稽核；來源 migration、
   共享 edoc namespace forward 和 bootstrap/readiness gates 必須一致。
3. 在既有簽核頁集中「待交接」，使用既有 Finance 框架、原生選單、
   共用對話框焦點與錯誤反馈；伺服器確認後才顯示交接成功。
4. 補上追蹤責任、補正關聯新案及離職收件人通知重定向，測試完整閉環。
5. 隔離測試、瀏覽器驗收、真實 SSO 驗收、正式發布及讀取驗證。

不得把尚未完整串接的規劃器或 SQLite 測試當作正式功能已完成。

## 驗收矩陣

| 項目 | 驗收標準 |
| --- | --- |
| 新分頁 SSO | Finance/APM 已登入且有權限，EDOC 新分頁／直達／重新整理不重複要求登入；紀錄實際 OAuth 路徑，不偽造 handoff |
| 身分切換 | A 登出或切換 B 後，A 的草稿、列表、快取及延遲回應不得出現在 B；舊 token 不可簽核 |
| 權限撤銷 | 收到 Finance 停用／撤權資訊後伺服器拒絕敏感動作，無瀏覽器快取繞過 |
| 網路異常 | 網路失敗不同於未登入；可重試、不無限轉圈、不丟失尚未送出內容 |
| 審核人離職 | 離職帳號不能簽；交接未確認前不轉交；同公司適格接任人確認後須重新看檔再簽 |
| 申請人離職 | 原申請人仍保留；退回補正由接任人關聯建立新案，新案不帶入原核准、原用印、原發文字號 |
| 雙人／越權 | 同人提出確認、跨公司／租戶、停用接任人、自我簽核、繞過管理權限均拒絕 |
| 競爭／重試 | 簽核與交接競爭只有一方成功；相同請求安全重試不重複交接／通知，變更內容重用 ID 拒絕 |
| 已完成案件 | 不改已簽、用印、寄送資料；只交接後續追蹤；原案歷程與檔案可查 |
| 裝置操作 | 電腦／平板／手機不溢出；鍵盤可操作；錯誤保留输入，關閉對話框回到原按鈕 |
| 發布 | 完整隔離 DB／API／瀏覽器測試 + 五位本人 SSO + 人工確認後，才發布及驗證正式靜態版本／健康檢查 |

## 真實 SSO 執行方式

驗收採使用者已指定的五位角色本人操作；姓名不寫入公開測試資料或 fixture。
登入時由本人輸入帳密／MFA，工具不取得密碼、不簽發假 handoff、不代登入。
每位檢查跨模組、新分頁、直達、重新整理、重新登入與其角色工作流程。
正式案例以去識別化內容建立，不寄出真實公文。測試只保存角色、結果、
時間、錯誤碼與已遮罩證據；缺少本人實測時標記待驗，不標記通過。

## 本次不可隱藏的邊界

- 真實 SSO 需要本人實際登入；既有 synthetic 五帳號測試不是替代品。
- 不承諾第一次 Google OAuth、所有網路請求或大型 PDF 都在 0.5 秒內完成。
- 不改正式交換 provider，也不呼叫機關正式交換環境。
- 不改共享 Supabase 的 public schema，不重置正式資料，不回寫歷史 migration。

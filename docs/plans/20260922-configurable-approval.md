# 文件類型簽核設定與完整用印驗收

## 範圍

- 修正缺少申請資訊時誤報 PDF 上傳失敗；不將印章尚未啟用當成上傳障礙。
- 在系統設定保存正式、版本化、依文件類型區分的簽核節點。支援組織關係及指定 Finance 人員、新增、刪除及排序。
- 總務執行及申請人收件保留為系統階段。設定變更只影響新送簽，已送簽保留流程、人員、文件及印章版本快照。
- 正式流程提供通過、退回上一關、通過並加簽、申請人抽單。既有退回申請人補正另外保留。
- 完成隔離環境的實際瀏覽器流程與 PostgreSQL 原子交易驗證，驗證 PDF 輸出。不得以本機示意流程取代正式 API。

## 操作語義

- 通過：精準綁定當前關卡 ID、實際簽核人、鎖定文件雜湊及檢閱證據。
- 退回上一關：只有當前簽核人或有效代理；原因必填。新簽核代次保留前綴已簽歷史，上一關及後續關卡需重新簽核，第一關另使用退回申請人補正。
- 加簽：比照 Finance 的「核准本關，再排指定員工為下一關」。指定人員必須啟用、同一已驗證 Finance 範圍，排除申請人及操作人，原因與檢閱證據必填。不得以加簽繞過最後用印檢查。
- 抽單：只允許原申請人在正式用印／寄發前執行。取消舊 pending 關卡並複製可編輯 revision，舊原稿及簽核鎖定版不覆寫；再送簽須完整重走流程。
- 同時操作：精準關卡／版本 CAS；同 operation ID 只接受相同 actor、document、action 與 request hash 重試。

## 技術邊界

- `official-workflow-config` schema v3，依文件類型保存 `nodes`，每個節點有穩定 id/name/assignee；最多 12 個可編輯簽核節點。
- 設定 PATCH 採 `expected_version`，衝突回 409，不覆寫其他管理員修改。
- 新動作由 SQLite SAVEPOINT 與 Supabase 原子 RPC 保證一致性，正式 API 缺失即停止，不退回 localStorage 模擬成功。
- 共用 public 與 shared edoc schema 前向 migration；不重跑 bootstrap、不修改 Finance 組織來源、不開放瀏覽器直接 RPC。
- 公文指定人維持既有同公司授權；PDF V2 的跨公司指定人僅限同一已驗證 Finance 租戶與有效公司、人員，不把自訂流程當成擴權手段。
- 所有測試使用合成文件、印章與帳號。正式電子公文交換維持停用／Mock。

## 驗收

1. 桌機、手機：申請資料 → 上傳 → 加文字及大小章／騎縫章 → 保存重開。
2. 瀏覽器逐關檢閱原稿／編輯版並簽核，最後下載用印 PDF，檢查頁數、文字、原稿雜湊與實際印章像素。
3. 設定更新、設定衝突、舊案快照、不同文件類型路由。
4. 退回上一關、新增簽核人、抽單重編重送及重試冪等。
5. 未授權、跨租戶、自簽、停用人員、過期關卡、用印後抽單和同時操作拒絕。
6. 保留既有完整測試；分別列出本機、PostgreSQL、瀏覽器與正式環境證據，不混稱正式驗收。

本次未授權修改正式業務資料或啟用公司印章；若正式帳號或印章仍有缺口，須在交付明確列出，不能以合成驗收宣稱正式用印已通過。

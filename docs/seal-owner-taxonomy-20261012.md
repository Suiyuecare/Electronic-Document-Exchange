# 印章種類、數位缺件與鎖定版本

## 分類來源

印章的組織種類由具有 `seals.manage` 權限的既有 Finance 印章保管身份明確設定，存於 EDOC 的 `company_seal_policies`。它不是 Finance 公司名稱或組織資料，不得用公司名稱、章圖檔名、掃描文件文字自動推定。

未分類時可以管理、上傳及檢視歷史，但新申請的印章選擇與新增章位都必須拒絕；後端回傳 `seal_owner_classification_required`，不能以隱藏選項取代權限檢查。

| 明確種類 | 必備數位槽 |
| --- | --- |
| 公司 | 公司章大、小；便章大、小；連續章單枚 |
| 機構 | 圖記章大、小；便章大、小；連續章單枚 |
| 未分類 | 便章大、小與連續章列為共同數位槽；兩組主章僅列條件槽，須先分類才能作完整結論 |

既有 ID 與類別 code 保留：`establishment_seal` 顯示公司章、`general_seal` 顯示便章、`official_seal` 顯示圖記章。新連續章採 `continuous_seal`／`single_seal`。銀行章與其他章保留管理及歷史回放，不借用為新三類用印選項，也不列入五個必備槽。

## 數位缺件不等於實體缺章

缺件盤點回傳 `physical_inventory_verified: false`。`missing_record`、`missing_current`、`unusable_current` 都表示數位章槽或可用電子版本未齊備，不證明實體印章不存在。已交付的掃描來源也不等同於已完成去背、校準、上傳及設為 current。

盤點以類別與大小槽精確匹配；只有大章不能滿足小章。未分類組織不會被判定為完整可上線，主章條件槽不作缺實體章的結論。

## 可用性

新選項須同時符合：啟用、明確組織種類允許、current 檔案、已通過掃描、合法尺寸政策、原章檔案 metadata 的 ID／hash／大小／MIME／儲存定位吻合，以及原始儲存物件可用。

Supabase 的 metadata HEAD 不是 blob 存在證據。後端使用授權的單位元組 Range GET；只接受 `206`、精確 `Content-Range`、總長度吻合、單位元組回應。忽略 Range 的 `200`、轉址、錯誤或超時均不放行，也不讀完整 body。每次清單的探測共用兩秒上限；原章 URL、讀取位元組與定位資料不回傳前台、不存入報告或 log。

此探測只證明物件可讀，完整 bytes 的 checksum 仍由既有預覽／產出流程驗證。歷史鎖定版不要求 `is_current`，但仍需其原始版本與完整 hash 驗證，不得偷偷改用新版。

## 校準

公司章與便章沿用既有 `institution-seal-v2-calibrated` 正方形政策；既有 v1／v2 的已鎖版本保持原樣。

新圖記章使用 `official-seal-v1-calibrated`，連續章使用 `continuous-seal-v1-calibrated`。管理員必須量測並填入寬與高，不提供猜測的預設實體尺寸。圖記仍保留大／小槽，連續章為單枚。每軸需至少 250 DPI，圖片與實體校準比例須吻合。

各軸 1–200 mm 只是系統技術範圍，並非法律標準、推薦尺寸或任何章的實際尺寸。沒有圖片與量測資料時不得宣稱已完成校準。矩形政策不能被套到公司章或便章；API、資料庫 trigger 與已鎖位置皆驗證類別／尺寸／政策配對。

## 驗收

1. 合成公司與機構各自只有五個正確槽；未分類不能新用印。
2. 缺小章不借用大章、其他類別或他公司章。
3. 停用、缺 current、metadata 不吻合、遺失 blob、錯誤 Range、超時都不能新增章位。
4. 長矩形圖記章、橫向連續章按明確校準寬高上傳、保存、套印；既有正方形政策不放寬。
5. 已鎖版本換 current 後仍使用原 file ID／hash／尺寸／policy；分類變更也不能重寫歷史輸出。
6. 所有測試資料為合成章與去識別化文件；正式 Supabase 與機關交換未寫入或呼叫。

本文件及本機／隔離 PostgreSQL 通過不代表已部署，亦不代表實體章已全部補齊。

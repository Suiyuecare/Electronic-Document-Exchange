# eDoc 內部上線交接

版本：2026-10-08。範圍：內部公文、簽核、電子用印、收發管理。
只能選擇所選公司已啟用、可用的 current 印章款式；缺少的大小章或騎縫章款式不應顯示為可用選項。沒有可用章時仍可編輯並存草稿，但不能完成需要該章的用印送簽。政府正式電子交換維持 Mock／停用。

本輪六項工作為離職未結案件交接、真人跨模組 SSO／人員異動、上傳／多裝置效能、通知／收發閉環、備份／復原、操作手冊／介面文字。程式及隔離測試與正式驗收分開記錄；真人 SSO、實體手機、異地金鑰保管與連續 7 日備份證據仍 pending。發布程式不等於這些驗收已完成，也不代表政府正式交換可啟用。

## 工作分工

| 工作 | 主責角色 | 協助／升級 | 入口 |
|---|---|---|---|
| 人員、公司、部門、主管關係異動 | Finance 名冊管理者 | 行政部門主任 | Finance 名冊；eDoc 自動同步 |
| 員工首次登入與送件操作 | 總務 | 行政部門主任 | 首頁、簽核紀錄 |
| 簽核卡關或關係人不符 | 行政部門主任 | 所屬部門主任、執行長 | 簽核紀錄、Finance 主管資料 |
| PDF 上傳、格式、編輯或雲端保存問題 | 總務 | 行政部門主任、系統維護者 | 電子用印、系統設定 |
| 寄發與寄送證明 | 總務 | 行政部門主任 | 收發管理 |
| 告警、部署回復、備份還原 | 系統維護者 | 行政部門主任、執行長 | 系統設定、託管平台 |

告警從 Finance 同步名冊解析目前啟用的 `admin_director` 與 `ga_chief`，
逐一綁定使用者 ID、公司 ID 與帳號 Email；不以「同職稱第一人」替代實際對象。
角色停用或改派後，下次檢查重新解析。這是系統責任分工，不表示任何具名同仁已接受排班；
行政部門主任需確認上線日主責及備援人。

## 上線日作業

1. 開放前由行政部門主任查看就緒狀態及維運告警，先處理 critical 異常。
2. 各角色本人使用自己的登入狀態由模組入口進入，確認有權限的 Finance／APM／eDoc 可進出且不重複要求登入；新分頁也要驗收。確認預設公司、部門、待辦及收發入口；不要求或代用同仁密碼。
3. 員工由撰寫公文或電子用印建立新草稿；續寫既有案件由「草稿編輯」選擇，不自動覆蓋新輸入。A4 PDF 橫式、直式均可；非 A4 需先同意等比例轉為 A4 並確認預覽，原稿保留。上限 50 MB／300 頁。
   選檔後先在本機開啟預覽與編輯，雲端保存於背景進行。進度、未保存、保存中、已保存及失敗要能區分；送簽與切換案件前仍須完成雲端同步及預檢，不能把本機可編輯當作已保存成功。PDF 編輯上傳沒有掃毒步驟，保留登入／案件權限、檔案類型、大小、頁數、結構與雜湊校驗；不把 `not_scanned` 寫成掃描通過。圖片／印章等另受其既有安全政策約束。
4. 送簽前確認附件及簽核人；鎖定後不得直接修改本文、附件、章位。
5. 退回上一關、否決、加簽與申請人抽單依當次狀態及授權操作，不以直接修改資料繞過流程。需要修改本文、附件或章位時建立新 revision，重新簽核，不沿用舊版核准；進入申請人收件確認、用印工作已認領／開始、已完成或已寄發等不可抽單的階段須由系統拒絕並保留歷程。申請人離職且退回補正時，由接任人建立關聯原案的新申請，原案與原申請人保留；交接候選需核准後才生效，不自動冒用離職人的身分。
6. 用可用公司章完成用印後，申請人及原簽核關係人依權限下載。須驗收實際產出 PDF 可開啟、章款／位置／尺寸正確、透明 PNG 章層在最上層；頁面顯示完成不能取代產出檔案檢查。
7. 由總務依核准方式寄出，再回填日期、方式、對象及寄送證明。
8. 下班前核對待簽、待寄發及通知失敗，未結問題交行政部門主任。

## 通知與監控

狀態區分「憑證已設定」、「通知通道已接受請求」、「人員實際收到」與「已讀」。
Email／webhook 等 provider receipt 只證明服務接受請求，不等於送達或已讀；收件者確認要另外留存。站內已讀與外部通道接受不得互相代填。未設定、失敗、逾時或只完成本機排程都不能顯示已送達；重送成功保留原失敗歷程。

監控 webhook 未設定或失敗時，沿用 Email 及個人站內通知提醒值班角色；同一批錯誤碼、
等級及使用者，critical 每小時最多一筆，warning 每日最多一筆。未設定 Sentry 等長期建議不寄通知。
外部通知只含等級及錯誤碼，詳細內容留在具管理權限的維運中心。
Email 憑證失效時仍保留站內提醒。不使用 LINE 的內部範圍不以缺少 LINE 憑證報警。
成功重送後清除對應通道的待處理失敗數，歷史紀錄保留。

`GET /api/production/monitoring` 的 `checks.alertDelivery` 是不寄信的預覽，
可核對 provider、精準收件人 ID 與 `fallbackReady`。執行監控檢查才會派送有需要的告警。
`GET /api/notifications/gateway-status` 的 `runtimeReadiness` 反映即時設定與服務接受紀錄，
不以舊的 `notification_readiness` 初始化字串作為寄送開關。

## 問題處置

| 問題 | 第一動作 | 升級或停止條件 |
|---|---|---|
| 模組無法登入 | 查 Finance 人員啟用及公司開放，保留錯誤碼與時間 | 多人同時失敗交維護者，暫停新送件 |
| 公司、部門或主管不符 | 在 Finance 修正，確認同步後重整 | 不在 eDoc 另建帳號或手改主管來規避 |
| PDF 上傳或保存失敗 | 核對 PDF 類型、50 MB／300 頁限制、非 A4 轉換同意及預覽，區分本機編輯與雲端保存，保留錯誤碼 | 沒有掃毒等待步驟；權限、結構、頁數、大小或 hash 異常仍須停止送簽，保存草稿並重試，不假顯示已保存 |
| Email 未收到 | 查派送紀錄、receipt，請本人查垃圾信 | 重送仍失敗交維護者；站內待辦持續有效 |
| 排程或服務 critical | 查 healthz、readyz、Cron 時間及 runtime logs | 行政主任升級執行長決定是否暫停服務 |
| 疑似遺失或越權 | 停止相關變更，保存 ID、時間、遮罩錯誤碼 | 不直接覆蓋正式庫，先隔離還原與核對 |

## 備份與回復

備份驗收範圍須同時涵蓋 `edoc`／`edoc_private` 資料庫及兩個 private Storage 的實際 bytes；SQLite 只適用本機測試。本輪本機隔離還原與 receipt 校驗測試不代表例行正式備份已啟用。
隔離還原需留存筆數、資料／物件 hash、權限及實測 RTO/RPO。遠端 runner 要回傳完整原始 receipt、重算 canonical hash，且 `receipt_id` 綁定當次 request `drill_id`；只有 hash 格式、歷史 receipt 或 `ok` 摘要不能通過。既有 receipt 不驗證 PDF 開啟、異地 bytes 或新 Storage API，需分別另測。
設定備份或產生 export 不等於完成還原演練；異地副本取回、異地金鑰保管、非互動排程及連續 7 日成功／失敗／補跑證據仍 pending。參見 `docs/backup-restore-drill.md`。

每次發布前從平台讀回並核實專案、環境、來源 commit、目前部署及健康檢查，將相容且已驗證的上一版部署記入當次發布紀錄。本文件不指定未重新驗證的舊 deployment ID 作為回復候選。
程式異常依 `docs/production-monitoring-runbook.md` 回復；先核對資料庫／檔案結構相容性。程式 rollback 不等於資料 rollback，不得直接以舊備份覆寫後續正式案件。保留未結任務、不可變檔案及稽核歷程後，再決定隔離還原與資料修復。

## 尚待正式驗收

- 員工、主管、總務、行政部門主任、負責人本人完成跨模組／新分頁 SSO、送件／簽核及離職未結案件接任測試；名冊與權限變更須實際讀回。
- 電腦、平板與實體手機實測，含弱網、斷線重試、PDF 開啟、雲端保存及實際產出；模擬 viewport 不取代實體手機。0.5 秒工作區可互動／2 秒本機可編輯是驗收目標，須記錄檔案大小、頁數、裝置、網路與樣本，不能對所有檔案無條件承諾。
- 通知通道接受與本人收到／已讀、收文派發與回覆時效，分別留存證據。
- 備份異地 bytes 取回還原、金鑰保管及連續 7 日例行證據；沒有證據維持 pending，不以發布完成替代。

## 必須留存

- 上線日主責與備援人的實際排班確認，以及既有聯絡方式。
- 去識別測試報告：角色、帳號 ID、案件 ID；不得放私密本文或印章原圖。
- 郵件服務 receipt 與收件者確認分開記錄。
- 新部署與回復候選 ID、健康檢查、備份及隔離還原證據。
